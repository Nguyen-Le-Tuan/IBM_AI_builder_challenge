**Reading of section 1.** The documented clean path is: the user right-clicks the image (or selects the post and clicks Check), the service worker or offscreen document fetches the image URL with a host permission for the CDN (requested at runtime), and decodes it. `captureVisibleTab` is the fallback when the URL cannot be fetched; it is limited to 2 calls per second and to what is on screen.

**Reading of section 2.** Only Tesseract.js documents word-level boxes in the browser today. PaddleOCR.js gives line polygons and is officially supported but young (0.x). TextDetector and Gemini Nano do not give a usable, shipped box API. On the server, Docling gives element-level boxes, and Granite-Docling gives element-level `<loc>` boxes; neither documents word boxes for images. Sending image pixels to the backend is a change to the D-006 data-handling rule and needs a team decision.

### 3a. CSS Anchor Positioning

## Comparison

| Layer | Option | Strengths | Costs and risks |
|---|---|---|---|
| Pixels | Service worker / offscreen `fetch` of the image URL | Full-resolution bytes; no canvas tainting; the URL comes from a user right-click (`srcUrl`) | Needs a host permission for each image CDN (runtime `optional_host_permissions` prompt, or broad hosts that the store reviews); must never let the content script choose arbitrary URLs; the fetched variant may differ from the displayed one |
| Pixels | `captureVisibleTab` crop | `activeTab` only; captures what is on screen, including CSS backgrounds and canvas (protected video unknown) | Visible area only; 2 calls/s; screen resolution, not source resolution; includes anything covering the image; DPR/zoom mapping undocumented |
| Pixels | Canvas in content script | No extra permission | Tainted for almost every cross-origin feed image; not reliable |
| OCR | Tesseract.js 7 (bundled, offscreen document) | Word, line, paragraph boxes; Apache-2.0; about 3 MB WASM + about 3 MB English data | CPU only; printed text only; accuracy on stylised meme fonts unknown; worker memory is high |
| OCR | PaddleOCR.js 0.4.x | Official PP-OCR in the browser; Apache-2.0; WASM or WebGPU through ONNX Runtime Web | Line polygons only; 0.x API; about 6–21 MB models plus about 15 MB ORT WASM plus OpenCV.js; defaults load from remote hosts |
| OCR | Docling / Granite-Docling on the backend | IBM stack; element boxes; strong document parsing | Image leaves the browser (needs a change to D-006); element-level, not word-level, boxes; server cost and latency |
| OCR | `TextDetector`, Gemini Nano | No download / on-device | `TextDetector` is behind a flag; the Prompt API returns text only and needs 22 GB disk and a strong GPU or 16 GB RAM |
| Overlay | JS tracker + fixed shadow-root layer | Works in every browser; no change to page DOM; full control | More code; main-thread updates can trail compositor scrolling; must handle nested scrollers |
| Overlay | CSS anchor positioning | Browser keeps boxes glued while scrolling; `position-visibility` hides boxes when the image is clipped | Must write `anchor-name` onto the page's `<img>`; cross-tree matching unproven; ignores transforms; full `position-anchor` only in recent releases |
| Overlay | Wrap the `<img>` (Annotorious style) | Simplest geometry | Moves the page's own node; likely to fight framework re-renders |

## Needs a spike

Use team-made test images and a local fixture page that imitates a feed. Do not browse or scrape social platforms for these spikes.

1. **Cross-tree anchoring.** In current Chrome stable, does a `position-anchor` written in an extension shadow root find an `anchor-name` set on a light-DOM `<img>`? Does `showPopover({ source: img })` give an implicit anchor across trees?
2. **Anchoring inside a virtualised feed.** Do boxes follow the image inside a nested scroll container, and does `position-visibility: anchors-visible`/`anchor-visible` hide them when the image is clipped? What happens when the framework re-renders and drops our inline style or attribute?
3. **`captureVisibleTab` geometry.** Output pixel size versus CSS pixels at devicePixelRatio 1, 1.25 and 2 and at 90%/125% zoom; crop error in pixels.
4. **Tesseract.js 7 in MV3.** Bundled worker and core in an offscreen document with `'wasm-unsafe-eval'`: cold-start time, memory, and word-box accuracy on about 20 headline screenshots and infographics.
5. **PaddleOCR.js versus Tesseract.js** on the same set: recall on stylised text, and whether line polygons can be split into words well enough for phrase highlights.
6. **Re-fetch fidelity.** Does fetching `currentSrc` from the extension return the same pixels as displayed (same `srcset` variant, no cookie or referrer requirement)?
7. **Hash stability.** SHA-256 and perceptual hash (blockhash, Jimp pHash, PDQ) on re-encoded and resized copies of text-heavy images; false-match rate between similar headline cards.
8. **Docling on images.** On a PNG input, which OCR engine fills `word_cells`, and how fast is it on CPU? How precise are Granite-Docling `<loc>` boxes on a single-headline screenshot?

## Recommendation

`RECOMMENDED (not decided)`

1. Image support changes D-006 (today: selected text only). Log a team decision before building it.
2. Entry point: a context-menu item on images (grants `activeTab`, gives `srcUrl`). Fetch bytes in the offscreen document with a runtime-requested host permission for that CDN; fall back to a `captureVisibleTab` crop if the user declines.
3. OCR in the browser with Tesseract.js 7, bundled locally (no CDN code), in an offscreen document with the `WORKERS` reason, using `blocks` output for word boxes. Run spike 5 before committing; keep Docling/Granite-Docling for an optional server mode only if the team accepts sending images.
4. Overlay: build the JavaScript tracker in a fixed shadow-root layer as the baseline. Add CSS anchor positioning as an enhancement only if spikes 1–2 pass.
5. Store boxes as fractions of the OCR'd bitmap, key cached results by SHA-256 plus a perceptual hash, and re-attach on `MutationObserver` events.
6. Layer `pointer-events: none`; small focusable boxes; hover card that meets WCAG 1.4.13.
7. Product code for this goes through IBM Bob per the team rule; this note is research only.
